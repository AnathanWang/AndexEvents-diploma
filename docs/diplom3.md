**3 Проектирование программного продукта**

**3.1 Архитектура программного решения**

В рамках реализации программного продукта была выбрана микросервисная многоуровневая архитектура клиент-серверного типа. Такое архитектурное решение обеспечивает высокую масштабируемость, отказоустойчивость, удобство разработки и сопровождения системы.

Система разделена на несколько независимых слоёв и компонентов, каждый из которых выполняет строго определённые функции:

- клиентский слой - кроссплатформенное мобильное приложение на Flutter (Dart SDK ^3.9.2), обеспечивающее взаимодействие пользователей с системой. Приложение не содержит бизнес-логики обработки данных и полностью отделено от серверной части; вся логика управления состоянием реализована через архитектурный паттерн BLoC;
- API-шлюз - Traefik v3.0, единая точка входа для всех запросов. Работает на порту 80, выполняет проксирование и прозрачную маршрутизацию входящих HTTP-запросов на целевые микросервисы по правилам, сконфигурированным через метки Docker-контейнеров;
- сервисный слой на Java - три Spring Boot 3.3.5 сервиса (auth-service, users-service, events-service), реализующие основную бизнес-логику: верификацию токенов, управление профилями пользователей, геолокационный поиск событий и пользователей;
- сервисный слой на Go - два высокопроизводительных сервиса (match-service, upload-service) на Go 1.23+ с фреймворком Gin, предназначенных для задач с высокими требованиями к конкурентной производительности: обработки свайпов и потоковой загрузки файлов;
- слой хранения данных - единая физическая база данных PostgreSQL 16 с расширением PostGIS, разделённая на логические схемы по принципу Single Database, Multiple Schemas; управление версиями схем осуществляется инструментом Flyway при старте каждого Java-сервиса;
- объектное хранилище - MinIO S3 для хранения медиаконтента пользователей и событий; полностью совместимо с Amazon S3 API, развёртывается локально в Docker-контейнере;
- кэш - Redis 7 для хранения временных данных и сессий.

Особое внимание уделено разделению ответственности между компонентами. Выбор двух языков программирования для серверной части продиктован разными требованиями к задачам: Java 21 со Spring Boot обеспечивает зрелую экосистему, развитые инструменты безопасности и объектно-реляционное отображение для бизнес-сервисов; Go 1.23+ с Gin обеспечивает высокую конкурентную производительность через горутины и каналы для высоконагруженных сервисов - обработки свайпов и потоковой передачи бинарного контента.

Вся инфраструктура полностью контейнеризирована с помощью Docker и управляется через Docker Compose, что обеспечивает воспроизводимость среды и позволяет запустить все пять микросервисов, базу данных, кэш и объектное хранилище одной командой make up.

**3.2 Процессы системы**

**3.2.1 Регистрация, авторизация пользователя и разграничение прав доступа**

Процесс аутентификации в системе построен на принципе делегирования: само управление учётными данными полностью передано провайдеру Firebase Authentication, а серверная часть выполняет исключительно верификацию выданных Firebase токенов, не хранит паролей и не управляет сессиями.

Жизненный цикл аутентификации включает следующие этапы. Пользователь открывает мобильное приложение и проходит процедуру входа через Firebase Authentication SDK - по электронной почте и паролю или через поддерживаемые социальные провайдеры (Google, Apple ID). Firebase выдаёт мобильному клиенту временный JSON Web Token - Firebase ID Token. Клиентское приложение сохраняет токен в провайдере состояния IdTokenProvider и подкладывает его к каждому исходящему запросу в HTTP-заголовок Authorization: Bearer &lt;token&gt;. Traefik доставляет запрос к целевому микросервису, где настроен Spring Security фильтр (для Java-сервисов) или middleware (для Go-сервисов). Сервис скачивает и кэширует публичные ключи подписи Google с JWKS endpoint, криптографически верифицирует токен и извлекает uid пользователя - уникальный Firebase-идентификатор. Если верификация прошла успешно, uid сопоставляется с внутренним идентификатором пользователя в базе данных через auth-service.

Разграничение прав доступа реализовано через ролевую модель. В базе данных введён перечислимый тип UserRole со значениями USER, MODERATOR и ADMIN. Роль пользователя хранится в таблице User и используется на сервере в аннотациях Spring Security, таких как @PreAuthorize("hasRole('ADMIN')"), которые блокируют выполнение метода при несоответствии роли. В Go-сервисах аналогичная логика реализована через middleware-функции, проверяющие роль пользователя до передачи запроса в handler.

**3.2.2 Заполнение профиля и прохождение онбординга**

Процесс онбординга - обязательный шаг для каждого нового пользователя, гарантирующий, что в системе не появляется пустых профилей без минимального набора данных. Онбординг управляется флагом isOnboardingCompleted в таблице User: пока флаг имеет значение FALSE, мобильное приложение перенаправляет пользователя на экраны заполнения профиля.

Процесс включает следующие шаги. При первой авторизации users-service создаёт запись в таблице User с uid из Firebase-токена, email и значением isOnboardingCompleted = FALSE. Мобильное приложение обнаруживает незавершённый онбординг и запускает пошаговый мастер заполнения профиля - не более 5 шагов: загрузка фотографии, ввод отображаемого имени, возраста, пола, описания (bio) и интересов. На последнем шаге пользователь настраивает параметры приватности: видимость профиля (isProfileVisible), видимость местоположения (isLocationVisible) и параметры поиска (minAge, maxAge, maxDistance). После подтверждения всех шагов выполняется запрос PATCH /api/users/me с установкой isOnboardingCompleted = TRUE, после чего пользователь получает доступ к полному функционалу приложения.

**3.2.3 Обновление геолокации пользователя**

Обновление координат является фундаментальным процессом всей платформы, так как от актуальности геоданных напрямую зависит качество ленты событий и рекомендаций матчинга.

Мобильное приложение подписывается на поток обновлений местоположения устройства с использованием стандартных платформенных API - GPS на Android и Core Location на iOS. При каждом значительном изменении положения пользователя (смещение более 100 метров от последней зафиксированной точки) или по истечении тридцати секунд активного использования приложение отправляет запрос PUT /api/users/me/location с телом { latitude, longitude }. **3.2.4 Публикация стихийного события**

Публикация стихийного события - ключевой краудсорсинговый процесс платформы, обеспечивающий формирование живой карты городской активности в режиме реального времени.

Пользователь нажимает кнопку публикации события на экране карты. Мобильное приложение автоматически заполняет поля координат текущим местоположением пользователя. **3.2.5 Геолокационный поиск событий**

Геолокационный поиск событий использует пространственные возможности расширения PostGIS, что принципиально отличает его от наивных запросов по диапазону координат.

Мобильное приложение отправляет запрос GET /api/events с параметрами latitude, longitude и maxDistance (в метрах). Events-service формирует SQL-запрос с функцией PostGIS ST_DWithin, которая вычисляет расстояния по геосфере земли, а не по плоскому декартовому пространству. Это обеспечивает метрически точные результаты - в отличие от фильтрации по диапазону координат, дающей ошибку на больших расстояниях. Запрос использует пространственный индекс по полям координат таблицы Event, что обеспечивает выполнение запроса за время, не превышающее 1 секунды даже при большом количестве событий. Результат возвращается в виде массива карточек событий, отсортированных по расстоянию от запрошенной точки. Мобильное приложение отображает маркеры событий на карте Яндекса и параллельно формирует вертикальную ленту карточек.

**3.2.6 Участие в событии (чек-ин)**

**3.2.7 Обработка свайпов и генерация взаимного совпадения**

Обработка свайпов является высоконагруженным процессом, для которого выделен отдельный сервис match-service на языке Go, обеспечивающий высокую конкурентную производительность через горутины и неблокирующий I/O.

Пользователь просматривает ленту рекомендаций - профили потенциальных знакомств, подобранные алгоритмически по геолокации или по участникам конкретного события. При действии свайп вправо (LIKE) или свайп влево (DISLIKE) мобильное приложение отправляет запрос POST /api/matches/like или POST /api/matches/dislike с идентификатором целевого пользователя в теле запроса. Match-service принимает запрос, записывает действие в базу данных и выполняет проверку наличия встречного LIKE от целевого пользователя. Если встречный LIKE зафиксирован, сервис генерирует сущность Mutual Match - взаимное совпадение - и инициирует отправку push-уведомлений обоим пользователям через Firebase Cloud Messaging. Оба пользователя получают push-уведомление вида «It's a match!» и видят друг друга в разделе взаимных совпадений.

Выбор Go для данного сервиса обусловлен тем, что горутины обрабатываются на уровне среды выполнения без создания системных потоков, что позволяет match-service обслуживать тысячи одновременных запросов свайпов при минимальном потреблении ресурсов.

**3.2.8 Загрузка медиаконтента**

Процесс загрузки медиаконтента реализован через выделенный upload-service на Go, обеспечивающий потоковую передачу бинарных данных напрямую в объектное хранилище MinIO S3 без промежуточной буферизации в памяти сервера.

Пользователь выбирает фотографию в мобильном приложении - при создании или редактировании профиля либо при публикации события. Мобильное приложение формирует Multipart/form-data запрос и отправляет его на POST /api/upload с параметром bucket=avatars (для фотографий профиля) или bucket=events (для медиаматериалов события). Upload-service принимает запрос, выполняет валидацию типа файла (допустимые форматы: JPEG, PNG, WebP) и размера. Валидированный файл передаётся потоком напрямую в MinIO S3 через S3-совместимый API - без создания временного файла на сервере. MinIO формирует публичный URL загруженного объекта, который upload-service возвращает клиенту в теле ответа. Мобильное приложение сохраняет полученный URL в соответствующем поле - photoUrl в профиле пользователя или в массиве медиаматериалов события.

**3.2.9 Формирование ленты рекомендаций матчинга**

Формирование ленты рекомендаций - алгоритмический процесс, определяющий, каких пользователей видит конкретный человек в разделе матчинга. Алгоритм реализован в users-service и работает в двух режимах: матчинг по городу и матчинг по событию.

При запросе ленты матчинга по городу мобильное приложение отправляет запрос GET /api/users/matches с параметрами maxDistance, minAge, maxAge и limit. Users-service выполняет SQL-запрос к таблице User с применением PostGIS функции ST_DWithin для выборки пользователей, находящихся в радиусе maxDistance метров от текущих координат запрашивающего пользователя. Запрос дополнительно фильтрует результаты по условиям: isOnboardingCompleted = TRUE, isProfileVisible = TRUE, возраст в диапазоне от minAge до maxAge, исключение самого пользователя и исключение пользователей, которым он уже поставил LIKE или DISLIKE. Частичный составной индекс по полям lastLatitude и lastLongitude с условием isOnboardingCompleted = TRUE AND isProfileVisible = TRUE обеспечивает высокую производительность этого запроса.

При запросе ленты матчинга по событию мобильное приложение дополнительно передаёт параметр eventId. В этом случае запрос включает JOIN с таблицей Participant схемы events - в результирующую выборку попадают только пользователи, зарегистрированные как участники данного события.

**3.2.10 Расчёт ключевых метрик**

Система автоматически поддерживает актуальность ключевых показателей для отображения в профиле пользователя и в карточках событий. К основным расчётным метрикам относятся:

- количество опубликованных событий пользователя - вычисляется COUNT-запросом к таблице Event с фильтром по authorId;
- количество взаимных совпадений пользователя - вычисляется COUNT-запросом к таблице Mutual Match в match-service с фильтром по userId;
- количество участников события - вычисляется COUNT-запросом к таблице Participant с фильтром по eventId;
- расстояние от текущего положения пользователя до события или другого пользователя - вычисляется функцией PostGIS ST_Distance в метрах с учётом кривизны земной поверхности;
- актуальность события - вычисляется на основе разницы между текущим временем и значением поля eventDate таблицы Event; события с истёкшей датой помечаются как завершённые.

**3.2.12 Управление настройками приватности**

Управление настройками приватности позволяет пользователю гибко контролировать своё присутствие на платформе - вплоть до полного исчезновения из поисковых выборок других пользователей без удаления аккаунта.

Пользователь переходит в раздел настроек профиля и видит панель управления приватностью. Доступны следующие параметры:

- видимость профиля (isProfileVisible) - при значении FALSE профиль полностью исключается из ленты рекомендаций матчинга всех пользователей на уровне SQL-запроса;
- видимость местоположения (isLocationVisible) - при значении FALSE координаты пользователя не передаются другим участникам и не используются в геолокационных выборках;
- минимальный возраст потенциальных знакомых (minAge) и максимальный возраст (maxAge) - фильтры применяются при формировании ленты рекомендаций;
- максимальный радиус поиска (maxDistance, в метрах) - ограничивает географический охват ленты матчинга; по умолчанию установлено значение 50 000 метров.

Изменённые настройки сохраняются запросом PATCH /api/users/me/settings в users-service и вступают в силу немедленно - следующий запрос ленты рекомендаций уже учитывает обновлённые параметры.

**3.2.13 Отправка push-уведомлений**

Система push-уведомлений построена на Firebase Cloud Messaging (FCM) и обеспечивает доставку уведомлений на устройства пользователей в режиме реального времени. На текущем этапе реализации push-уведомления отправляются при возникновении взаимного совпадения.

При регистрации в приложении мобильный клиент запрашивает у операционной системы разрешение на получение уведомлений. При генерации Mutual Match в match-service сервис извлекает FCM-токены обоих пользователей из базы данных и отправляет push-уведомления через Firebase Cloud Messaging API. Оба пользователя в течение нескольких секунд получают уведомление на экране блокировки устройства.

**3.3 Передача и хранение данных**

Подсистема передачи и хранения данных обеспечивает надёжное, безопасное и масштабируемое взаимодействие между всеми компонентами системы. Она связывает клиентский слой (мобильное приложение Flutter), серверный слой микросервисов и слой данных, гарантируя целостность, конфиденциальность и доступность информации на всех этапах работы платформы.

Основные компоненты подсистемы хранения: реляционная база данных - PostgreSQL 16 с расширением PostGIS, объектное хранилище - MinIO (S3-совместимое), кэш - Redis 7, взаимодействие между клиентом и сервисами - через REST API поверх HTTP.

Ключевые архитектурные свойства подсистемы:

- единая физическая база данных с логическим разделением по схемам (Single Database, Multiple Schemas) - схема users для таблицы User, схема events для таблиц Event и Participant; расширения PostGIS установлены в схеме public и доступны всем сервисам;
- версионирование схем через Flyway - каждый Java-сервис при старте автоматически применяет новые SQL-миграции к своей схеме, что исключает ручные операции с базой данных при обновлении;
- пространственная индексация координат через типы geography(Point, 4326) расширения PostGIS - обеспечивает метрически точные расчёты расстояний по геосфере земли вместо плоского декартового пространства;
- изолированное хранение медиаконтента в MinIO S3 по бакетам (avatars, events) - медиафайлы не занимают пространство реляционной базы данных и выдаются клиенту по публичным URL;
- стандартизированный формат ответа API: { success, data, message } - все пять сервисов возвращают ответы в единой структуре, упрощающей обработку на клиенте.

**3.3.2 Логическая модель данных**

На рисунке 3.14 представлена логическая модель базы данных, реализованная в соответствии с нормализованной схемой 3NF с применением паттерна Single Database, Multiple Schemas.

**Рисунок 3.14 - Логическая модель базы данных**

Основные сущности и связи:

- User (схема users) - центральная сущность, содержащая данные учётной записи, профиля, текущих координат, настроек приватности и фильтров поиска; связана отношением «один ко многим» с сущностями Event и Participant;
- Event (схема events) - описывает событие на карте: содержит идентификатор автора, координаты (latitude, longitude), тип события (SPONTANEOUS, PLANNED, ONLINE), категорию, описание, медиаматериалы и временные метки; связана отношением «один ко многим» с сущностью Participant;
- Participant (схема events) - связующая таблица «многие ко многим» между пользователями и событиями; содержит идентификатор пользователя, идентификатор события, роль участника (PARTICIPANT) и временную метку чек-ина;
- SwipeAction (схема matches) - фиксирует действие LIKE или DISLIKE одного пользователя в отношении другого; содержит идентификаторы инициатора и цели, тип действия и временную метку;
- MutualMatch (схема matches) - фиксирует взаимное совпадение двух пользователей; создаётся автоматически при обнаружении встречных LIKE; содержит идентификаторы обоих пользователей и временную метку.

**3.4 Серверная часть**

Серверная часть системы является ядром платформы и отвечает за выполнение всей бизнес-логики: верификацию токенов, управление профилями пользователей, геолокационный поиск, публикацию событий, обработку свайпов и хранение медиаконтента. Серверная часть построена на микросервисной архитектуре с чётким разделением на пять независимых сервисов, объединённых API-шлюзом Traefik.

Все сервисы работают в Docker-контейнерах, управляемых через Docker Compose. Для обеспечения автоматизации написан Makefile с командами make build-java, make up, make down и аналогичными, позволяющими управлять всем окружением из единой точки. Секреты (API-ключи Яндекса, Firebase Service Account, MinIO credentials) вынесены в файлы окружения .env, строго исключённые из системы контроля версий через .gitignore.

**3.5 Пользовательская часть**

Пользовательская часть системы реализована в виде кроссплатформенного мобильного приложения на Flutter (Dart SDK ^3.9.2), поддерживающего платформы iOS (минимальная версия iOS 13.0) и Android (минимальный API level 21) из единой кодовой базы. Приложение взаимодействует с серверной частью через REST API, использует Firebase ID Token для авторизации и получает уже обработанные и агрегированные данные. Всё взаимодействие с HTTP осуществляется через стандартный пакет http с обёртками логирования - без использования сторонних HTTP-клиентов.

**3.5.1 Интерфейс приложения**

Пользовательский интерфейс мобильного приложения Andex Events организован через нижнюю панель навигации (BottomNavigationBar), включающую четыре основных раздела:

Пользователи, не завершившие онбординг (isOnboardingCompleted = FALSE), автоматически перенаправляются на экраны заполнения профиля независимо от попытки доступа к любому другому разделу. Приложение поддерживает тёмную и светлую цветовые схемы, адаптируясь к системным настройкам устройства.

**3.5.2.1 Авторизация и регистрация**

Первый экран, который видит пользователь - экран авторизации. Он предоставляет два сценария: вход в существующий аккаунт и регистрация нового.

Онбординг активируется автоматически при первом входе и блокирует доступ к основным экранам до завершения.

Действия пользователя:

- шаг 1 - загрузить фотографию профиля (опционально, можно пропустить);
- шаг 2 - ввести отображаемое имя и возраст;
- шаг 3 - указать пол и выбрать интересы из предложенного списка;
- шаг 4 - написать краткое описание себя (bio);
- шаг 5 - настроить параметры поиска (минимальный возраст, максимальный возраст, максимальный радиус) и параметры приватности.

Результат действий пользователя:

- данные профиля сохранены в таблице User через запросы к users-service;

**3.5.2.3 Карта событий**

Карта событий является главным экраном приложения и отображает актуальную городскую активность в режиме реального времени.

Действия пользователя:

- открыть вкладку «Карта» через нижнюю навигацию;

**3.5.2.4 Лента событий**

- просмотреть список участников события с краткими профилями.

Результат действий пользователя:

- чек-ин зафиксирован в таблице Participant, пользователь включён в список участников;
- при переходе к матчингу по событию - экран матчинга открывается с фильтром по участникам данного события;
- счётчик участников события обновляется.

**3.5.2.6 Публикация события**

Экран публикации события позволяет пользователю добавить стихийное, плановое или онлайн-событие на карту.

Действия пользователя:

- ввести название и описание события;
- выбрать тип события: стихийное (немедленная публикация), плановое (с указанием даты и времени) или онлайн;
- выбрать категорию события из предложенного списка;
- при необходимости скорректировать местоположение на мини-карте;
- прикрепить фотографии или видео;
- нажать кнопку «Опубликовать».

Результат действий пользователя:

- медиафайлы загружены в бакет events MinIO S3 через upload-service; получены публичные URL;
- событие создано в таблице Event через запрос POST /api/events;
- событие появляется на карте у пользователей в радиусе в режиме реального времени.

**3.5.2.7 Матчинг**

Экран матчинга предоставляет ленту потенциальных знакомств в двух режимах: по городу и по событию.

Действия пользователя:

- открыть вкладку «Матчинг» через нижнюю навигацию;
- выбрать режим: матчинг по городу или матчинг по событию;
- просмотреть карточку профиля - фотографию, имя, возраст, описание, расстояние и интересы;
- выполнить свайп вправо (LIKE) или влево (DISLIKE) либо нажать соответствующую кнопку.

Результат действий пользователя:

- действие LIKE или DISLIKE передано в match-service через запрос POST /api/matches/like или POST /api/matches/dislike;
- при взаимном совпадении - отображается анимированное уведомление «It's a match!» и оба пользователя получают push-уведомление через FCM;
- следующая карточка профиля загружается из ленты рекомендаций.

**3.5.2.8 Взаимные совпадения**

Экран взаимных совпадений отображает список пользователей, с которыми зафиксировано взаимное совпадение.

Действия пользователя:

- открыть раздел «Совпадения» внутри вкладки «Матчинг»;
- просмотреть список взаимных совпадений с фотографиями и именами;
- нажать на карточку совпадения для перехода к полному профилю пользователя.

Результат действий пользователя:

- отображается актуальный список взаимных совпадений пользователя;
- при нажатии на карточку - открывается профиль совпавшего пользователя с информацией и интересами.

**3.5.2.9 Профиль и настройки**

Экран профиля предоставляет доступ к личным данным, статистике и настройкам аккаунта.

Действия пользователя:

- открыть вкладку «Профиль» через нижнюю навигацию;
- просмотреть счётчики активности: число опубликованных событий, число взаимных совпадений;
- нажать кнопку «Редактировать» для изменения фотографии, имени, описания или интересов;
- перейти в раздел «Настройки приватности» для управления видимостью профиля и местоположения;
- перейти в раздел «Фильтры поиска» для настройки minAge, maxAge и maxDistance;
- нажать кнопку «Выйти» для завершения сеанса и очистки токена авторизации.

Результат действий пользователя:

- изменения профиля сохранены в базе данных через запрос PATCH /api/users/me;
- настройки приватности вступают в силу немедленно для всех последующих запросов;
- при выходе токен очищен из IdTokenProvider, пользователь перенаправлен на экран авторизации.

**3.5.4 Ролевые особенности интерфейса**

Для обеспечения удобства работы и разграничения функционала в интерфейсе реализованы следующие ролевые особенности:

- пользователь с ролью USER видит только свои опубликованные события, свои взаимные совпадения и доступные события в радиусе поиска; все административные и модераторские функции скрыты;
- пользователь с ролью MODERATOR дополнительно видит пункт меню «Модерация», позволяющий просматривать и удалять события любых пользователей, нарушающих правила платформы;
- пользователь с ролью ADMIN имеет доступ к административной панели с управлением ролями пользователей и возможностью блокировки аккаунтов; функциональность отображается только при наличии соответствующей роли в профиле.

Проверка роли осуществляется на двух уровнях: на стороне сервера через аннотации Spring Security и middleware Go, а также на стороне клиента - BLoC-состояние UserBloc хранит роль авторизованного пользователя и управляет видимостью соответствующих элементов UI через условный рендеринг Flutter-виджетов.

**3.5.5 Безопасность и UX-детали**

Для обеспечения безопасности и улучшения пользовательского опыта в приложении реализованы следующие меры:

- все HTTP-запросы к серверу защищены Firebase ID Token, передаваемым в заголовке Authorization: Bearer &lt;token&gt;; токен имеет ограниченный срок жизни (1 час) и автоматически обновляется Firebase SDK при истечении;
- при истечении токена или ошибке авторизации (HTTP 401) приложение автоматически инициирует процедуру обновления токена через Firebase SDK; при неудаче - перенаправляет пользователя на экран авторизации с уведомлением;
- координаты пользователя передаются на сервер только при наличии разрешения приложения на доступ к геолокации устройства; при отсутствии разрешения геолокационные функции отображают предупреждение;
- фотографии профиля и медиаматериалы событий хранятся в изолированном объектном хранилище MinIO S3 с разграничением по бакетам; прямой доступ к бакетам без URL недоступен;
- все формы ввода снабжены клиентской валидацией; при ошибках сервер возвращает поле message в стандартизированном ответе, которое отображается пользователю во всплывающем уведомлении (SnackBar);
- пользователи с isProfileVisible = FALSE полностью исчезают из ленты матчинга и поиска - без удаления аккаунта и без необходимости обращения в поддержку.

**3.6 Подсистема push-уведомлений и интеграция с Firebase Cloud Messaging**

Подсистема push-уведомлений обеспечивает оперативное информирование пользователей о взаимных совпадениях без необходимости постоянного пребывания в приложении. Архитектурно подсистема является частью match-service и использует Firebase Cloud Messaging как транспортный слой.

На рисунке 3.17 представлена схема последовательности процессов подсистемы уведомлений.

**Рисунок 3.17 - Последовательность процессов подсистемы push-уведомлений**

Основные задачи подсистемы:

- хранить FCM Device Token каждого пользователя в поле fcmToken таблицы User;
- при генерации Mutual Match извлекать FCM-токены обоих пользователей из базы данных;
- формировать тело push-уведомления с заголовком «It's a match!» и текстом сообщения;
- доставлять уведомление через Firebase Cloud Messaging API на устройства обоих пользователей;
- обрабатывать ошибки доставки - если FCM-токен недействителен, помечать его как устаревший и исключать из последующих попыток отправки.

**3.7 Вывод по проектированию программного продукта**

В ходе настоящего раздела выполнено полное формальное описание архитектуры системы, всех ключевых процессов, структур данных и пользовательского интерфейса, что позволило получить целостное и детализированное представление о разрабатываемом программном продукте.

Ключевые результаты проектирования сводятся к следующему.

В части архитектурных решений выбрана микросервисная архитектура с пятью независимыми сервисами (auth-service, users-service, events-service, match-service, upload-service), объединёнными API-шлюзом Traefik. Разделение серверной части на Java-сервисы и Go-сервисы обосновано различными требованиями к задачам: Java 21 / Spring Boot обеспечивает зрелую экосистему для бизнес-логики, Go / Gin - высокую конкурентную производительность для высоконагруженных операций.

В части проектирования базы данных принят паттерн Single Database, Multiple Schemas, при котором единая физическая база данных PostgreSQL 16 разделена на логические схемы users, events и matches. Ключевым решением является применение расширения PostGIS с типом geography(Point, 4326) для хранения координат и функции ST_DWithin для геолокационных выборок, что обеспечивает метрически точные расчёты расстояний по геосфере земли. Частичный составной индекс по координатам пользователей с условиями isOnboardingCompleted = TRUE AND isProfileVisible = TRUE обеспечивает высокую производительность ленты рекомендаций матчинга.

В части пользовательского интерфейса спроектировано девять основных экранов мобильного приложения с детальным описанием каждого: действия пользователя, результаты этих действий и задействованные API-эндпоинты. Реализована ролевая модель интерфейса для ролей USER, MODERATOR и ADMIN. Архитектурный паттерн BLoC обеспечивает чёткое разделение бизнес-логики и UI-слоя, делая код тестируемым и расширяемым.
